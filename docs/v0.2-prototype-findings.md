# v0.2 prototype findings (T-008)

Release-gate results, run day-1 of v0.2 **before** the service architecture is committed, so a
failed spike re-plans the design early rather than late.

**Every measurement here is n=1**, taken on:

| | |
|---|---|
| OS | macOS, Darwin 25.5.0 |
| Arch | arm64 (Apple Silicon) |
| Node | v22.18.0 |
| Filesystem | APFS |
| Date | 2026-08-01 |

Nothing below is claimed for Linux, for other macOS versions, or for other filesystems. Where a
result is likely to be platform-specific, it says so.

Reproduce with `npm run spike:socket-cred` (prints the peer-UID probe's finding) and
`npm run test:spikes` (106 tests: the lockfile failure reproduction, the port primitive, the
bootstrap storm and crash matrix, lock-free publish, the credential fallback, criterion 6).
The suite must finish with **zero skips on macOS** and terminate on its own — no `--test-force-exit`,
which would hide exactly the handle, child-process and timer leaks these tests exist to expose.

## Question 1 — the locking primitive

> Is there a no-build locking primitive on macOS/Node 22 that survives crash, PID reuse, and
> unlink/recreate takeover races — and which candidate is it?

**Answer: GO — but NOT with either candidate.** Both A and B are lockfile designs and both are
**NO-GO**: a lock file outlives its owner, so it must be reclaimed, and Node exposes no atomic
compare-and-delete to reclaim it safely. Candidate B's failure is reproduced, not argued (§3.1).

The gate's answer is a **kernel-held loopback port bind**, which gives mutual exclusion and
crash recovery with no stale state to race over (§3.2). This is a "go" for v0.2 — the gate
decides *which* primitive ships, and finding that the assumed one cannot work is precisely the
outcome running it on day 1 is for.

## Question 2 — unix-socket peer credentials

> Can Node read the peer UID of a Unix-domain-socket connection on macOS without a native build?

**Answer: NO.** The specified fallback (0700 runtime dir + high-entropy 0600 token +
constant-time compare) is therefore what T-011 implements. This is still a "go" for v0.2 — the
gate decides *which* credential design ships, not whether v0.2 proceeds. Evidence in §2.

## 1. The finding that changed the design: macOS silently truncates socket paths

This one contradicts T-008's own acceptance criterion 5, which anticipated that "binding fails
past the measured macOS sun_path limit". **It does not fail.**

Measured by binding paths of increasing length and, for each, checking whether a socket file
exists at the requested path and whether a client can connect:

| requested path length | `listen()` | file at the requested path | client connects |
|---|---|---|---|
| ≤ 104 bytes | success | **yes** | yes |
| ≥ 105 bytes | **success** | **no** | **yes** |

Three separate things are wrong in the second row, and each is worse than a thrown error:

1. `listen()` invokes its success callback. No `error` event is emitted.
2. `server.address()` returns the **full, untruncated** path — so the API reports a path that
   nothing is listening on.
3. The socket is really created at the **104-byte prefix**. Measured directly: with a server
   bound to a 110-byte path, a client connecting to
   `<same first 104 bytes> + "COMPLETELY-DIFFERENT-SUFFIX"` connected and received the server's
   data.

So the hazard is not an error to handle — it is that **two distinct logical paths silently
collide onto one socket while every API reports success**. For a per-user runtime path that is a
correctness and isolation problem, not just a bug.

### Consequences for T-011

- The runtime path must be short **by construction**, not merely "usually short enough".
- The over-long path must be rejected **before `listen` is ever called**, on
  `Buffer.byteLength(canonicalPath) > 104`. A post-listen `lstat` of the requested path is
  **defence in depth only and cannot prove endpoint identity**: planting a real socket inode at
  the full requested path makes it pass while the true endpoint is still the truncated prefix —
  measured, and the reason plan review killed the post-listen guard as a primary check. It must
  never propagate into T-011 as one.
- The acceptance criterion is satisfied by *pre-bind refusal*, not by catching a bind failure.
  The deviation is deliberate and is recorded here rather than quietly reinterpreted.

### The path

`/tmp/spendbar-<uid>/svc.sock`. Both forms, since the guard measures the **canonical** one:

| | requested | canonical (`/private/tmp/…`) |
|---|---|---|
| uid 501 | 26 bytes | **34 bytes** |
| 10-digit uid | 33 bytes | **41 bytes** |

Every figure is well inside 104. The earlier text quoted "26 / 34" as if both were requested-form
bounds, conflating the two — the number that matters is the canonical column, because that is the
string the kernel sees.

Keyed on **uid, not username**. That is what bounds the length: criterion 5 asks about long
usernames and long home paths, and a uid-keyed path is immune to both by construction rather than
by being tested against a few long examples.

## 2. No peer-UID API exists in Node's stdlib

`net.Socket` — instance and prototype — exposes no property matching `/cred|uid|peer|ucred/i`
other than `_getpeername`, which returns an **address**, not credentials. There is no
`SO_PEERCRED` (Linux) or `LOCAL_PEERCRED`/`getpeereid` (macOS) binding. `process.getuid()`
reports the uid of *this* process, which answers a different question.

Reading peer credentials would need a native addon, which the no-build / no-lifecycle-script rule
forbids. Hence the fallback design in §4.

## 3. Locking — candidate comparison and evidence

### 3.1 Candidate B admits two simultaneous holders — reproduced

The design under test published a complete owner record via `link()` (create) or `rename()`
(takeover of a confirmed-dead owner), then decided the winner by **reading the lock back** and
checking whose random token was in it.

Read-back is a real improvement over trusting the syscall's return — but it is not exclusion.
Driving two contenders through the takeover window (`afterLivenessDecision` hook, so both read
the same stale record and both judge its owner dead):

```
A acquired: true   B acquired: true
*** BOTH ENTERED: true ***
```

A renames, reads back its own token, enters. B then renames over A, reads back *its* token, and
enters. Nothing revokes A. **Read-back can tell a process it lost; it cannot tell a process that
already won that it has since been superseded.**

This is not a patchable bug. Every race in the design comes from *reclaiming stale filesystem
state*, and the available primitives cannot do that safely:

| approach | why it fails |
|---|---|
| `stat` then `unlink` then create | TOCTOU: no inode-conditional delete, so it can delete a *different* contender's live lock |
| `link()` / `open(wx)` — never clobbers | safe, but a stale lock can then never be reclaimed at all |
| `rename()` — always clobbers | atomic, but atomicity only *orders* takeovers; it does not revoke the previous winner |
| `flock` / `O_EXLOCK` | not exposed by Node's stdlib; a native addon is forbidden here |

Candidate A (a third-party lockfile package) is rejected on the **same measured ceiling** — it has
only these same syscalls available — rather than on this repo's preference for zero dependencies.

### 3.2 What works: a resource whose lifetime the kernel owns

Bind `127.0.0.1:<port>` with `exclusive: true`. Measured:

| | want | measured |
|---|---|---|
| second bind while the holder is alive | `EADDRINUSE` | **`EADDRINUSE`** |
| bind after the holder is `SIGKILL`ed (no cleanup runs) | succeeds | **succeeds** |
| stale artefact to clean up after a crash | none | **none, by construction** |

The third row is the point. There is no file to reclaim, so the entire class of races in §3.1
does not exist — not "is handled", does not exist. The kernel releases the port when the process
dies, however it dies.

Costs, recorded rather than discovered later: it consumes a port; a sandbox that forbids loopback
binds breaks it and must be diagnosed as an environment failure rather than read as "lock held";
and it is machine-local, which is all v0.2 needs.

### 3.3 Consequence: snapshot publish needs no lock for STRUCTURAL integrity

Writing a complete temp file and `rename()`ing it over the target is atomic — a reader sees the
old file or the new one, never a torn one. That much is lock-free, and it retires the assumed
single-writer requirement *for corruption*.

It does NOT make concurrent publishes semantically safe, and §3.5 demonstrates the failure
rather than footnoting it: a slow writer that passed its dominance check can rename after a
newer writer and **regress the snapshot to stale state** (the read-then-rename TOCTOU,
reproduced deterministically in `publish.test.mjs`). Semantic freshness therefore relies on the
writer topology: every T-010 publisher goes through the single service holding the port lock.

The precise claim — the earlier "the advisory check never races" was stronger than the code
supports, and review round 5 was right to reject it: **the check does not race while the listener
is continuously held, which is the normal case.** It is not unconditional. Unexpected listener
loss is a genuine residual window: the kernel frees the port *before* JavaScript is dispatched the
`close` event, so a successor can acquire and publish while the former holder is still executing
and still believes it holds the lock. Two publishers can therefore overlap for that interval.
Atomic rename bounds the damage to a **stale-but-complete** snapshot, self-corrected by the next
dominating publish — never a torn one — and that bound, not exclusion, is what makes the window
tolerable. The same applies if the single-writer topology is violated outright.
For the snapshot writer specifically, the port lock is T-011's single-instance guard and nothing
more. T-013 separately reuses the same primitive, on its own allocation and `purpose`, for reader
computation leases — those are an optimisation (avoid duplicate work), not a correctness
boundary, now that publication is atomic.

### 3.4 The allocation must be write-once — "bind 0 and persist" is a split-owner race

Kernel exclusion applies only once every contender bids for the SAME address:port; port 0 is the
absence of that agreement. Measured with 8 real first-run children racing the naive scheme:

```
distinct candidate ports before publish : 8 of 8    <- eight singleton beliefs
```

Fix, measured with the same storm (`spikes/locking/bootstrap.test.mjs`): each child publishes its
candidate **write-once via `link()`**, which never clobbers; losers close their ephemeral listener
and bid for the winner's port, where the kernel rule finally applies:

```
distinct AGREED ports : 1        holders : 1        blocked : 7
```

`link()` is sound for the allocation and was fatal for the lock because an allocation is **never
reclaimed** — it is write-once configuration meant to outlive every process, so the unimplementable
reclaim step never arises. Consequences carried into T-011: no automatic re-allocation (identical
race); a foreign listener on the allocated port is a named error refusing startup; the allocation
file is coordination state validated fail-closed (owner, mode, type, encoding, range) — never
repaired in place. That refusal is **composed and driven**, not asserted: `startSingleton()` joins
`EADDRINUSE` → `identifyHolder()` → decision, and its tests require a foreign holder and an
unidentifiable holder each to throw `PortLockForeignHolder` **with the allocation file byte-identical
afterwards**. Review round 6 was right that the earlier wording claimed a composed behaviour that no
test exercised; the mutant it named — a caller that "recovers" by allocating a second port — is now
caught by that byte-identity assertion. `EADDRINUSE` is diagnosed with a domain-separated challenge–response over the
0600 token (protocol id + purpose + allocation id + the challenger's 256-bit nonce in the MAC),
because a bare HMAC over a nonce would authenticate ANY endpoint holding the per-user token — a
reader lease would impersonate the writer singleton. **Amendment against the plan**: the plan
specified a holder nonce as well; the implementation carries only the challenger's. The
challenger's fresh 256-bit nonce is what provides replay resistance (a captured reply is valid
only for the nonce it answered — tested with a genuinely-valid stolen reply), and a holder nonce
would add mutual authentication the diagnosis path does not consume: the CHALLENGER decides what
to do next, the holder decides nothing. Recorded as an amendment rather than silently narrowed.
Replay, wrong-purpose, and fragmented-nonce (TCP framing) cases are tested; the nonce is length-
framed at exactly 32 bytes and over-long requests are dropped without reply.

**Crash matrix** — `SIGKILL` at the REAL publication boundaries, driven by `publishAllocation`'s
own hooks so each row dies where its name says (the first matrix crashed outside the call, after
the `finally` had already tidied up, and so exercised none of them):

| crash point | allocation after | candidate residue |
|---|---|---|
| `before-publish` (nothing written) | absent | 0 |
| `mid-publish` (candidate durable, link not attempted) | absent | **1** |
| `after-link` (allocation live, cleanup not yet run) | the victim's | **1** |
| `after-lose` (loser dies before adopting) | the incumbent's, untouched | 0 |
| `after-adopt` (holder dies BOUND — the crash-recovery case) | the victim's | 0 |

A fresh, uninstrumented process converges on the persisted port with exactly one holder in every
row. The two residue-1 rows are the real cost of write-once publication: a stranded candidate is
**counted and left alone** — nothing may remove a candidate it did not create — and is proven
neither to block convergence nor to be adopted, since only the LINKED allocation is authoritative.

### 3.5 Limits, measured or reproduced rather than assumed away

- **The lock is held by a HANDLE.** The kernel frees the port when the listening socket closes —
  and before JavaScript is dispatched the `close` event, so a contender can enter while the old
  holder still runs. Exclusion holds exactly while the listener remains bound; an unrequested
  close raises a **named, positive lock-loss witness**. No abort-before-entry ordering is claimed
  (`portlock.test.mjs` records the contender may win first).

  What that witness does **not** do, corrected in review round 5: it does not stop anything by
  itself. `assertHeld()` is voluntary — a commit path that never calls it is never interrupted —
  and `onLost` is a constructor option a caller can override with a function that simply returns.
  The test proving a post-loss `assertHeld()` throws establishes the primitive works, not that
  every real commit consults it; a publish path with the guard deleted would survive that evidence
  untouched. So this is recorded as a **requirement on T-010/T-011, not a property of the lock**:

  1. every publisher calls `assertHeld()` **immediately before** its atomic commit, with no
     awaits in between;
  2. `onLost` must terminate the process or irreversibly disable publishing — returning quietly is
     not an allowed handler;
  3. the T-010/T-011 suite carries a mutant whose publish path omits (1) and **must fail**.

  Without those three, the witness is diagnostics rather than a safety property, and this document
  should not be read as claiming otherwise.
- **`exclusive: true` provides nothing here.** Measured: second bind gets `EADDRINUSE` with it
  false exactly as with it true. Retained as defence in depth, credited with no guarantee.
- **The tracked-connection teardown in `release()` is load-bearing and pinned.** It carried an
  "untested defence in depth" label for several rounds after three removal mutants survived. Those
  mutants survived because of how the property was measured, not because it was untestable: the
  assertion sat at 1900ms against a hard-coded 2000ms challenge deadline, so a release that waited
  the connection out landed at ~2000ms and any threshold loose enough to tolerate scheduler noise
  also admitted it. Making the deadline injectable (`serveIdentity({ challengeTimeoutMs })`) and
  pushing it to 30s separates correct behaviour from the mutant by three orders of magnitude; the
  mutant now dies. Recorded here because the stale label survived two rounds after the evidence
  changed, and a disclaimer that understates real coverage misleads downstream work just as a
  missing one would.
- **Snapshot publish** (`publish.mjs`): rename gives structural atomicity — the in-place mutant's
  two torn windows produce deterministic READ failures — both happen to die in `JSON.parse`, and a
  separate parseable-corruption test is what proves the checksum is load-bearing — while a reader walked into
  rename-publish's own widest window sees only complete snapshots. The dominance manifest is
  per-source offsets with incomparable-fails-closed (the scalar-max counterexample is a test).
  The advisory check's TOCTOU is **demonstrated, not hidden**: a writer held past its check does
  regress the target, completely, and the next dominating publish self-corrects.
- **Snapshot durability is scoped to process-crash atomicity, NOT power loss — by decision.**
  `publishSnapshot` does **not** `fsync` the temp file or its directory. The snapshot is a *derived
  cache* over the transcript logs: losing it to a power cut costs a recomputation, not data, and
  the next publish rebuilds it. Recorded here as a decision with a reason rather than left to read
  as an omission — and recorded in the **deliverable**, not only in the plan, because this is the
  document downstream tickets consult. The scope is exactly the snapshot; coordination state
  (the allocation and the credential token) *is* fsynced, including the link — see the next two
  bullets. T-010 currently specifies a snapshot fsync ordering that contradicts this; the conflict
  is filed as **ISS-030** and must be settled explicitly in one direction, not left as two
  documents disagreeing.
- A TCP port is machine-wide: another local user can hold it — refuse-to-start, never two writers.
- **Continuous reservation**: the publication winner's ephemeral listener IS the lock listener
  (`PortLock.adopt`), held from before the allocation named the port with no close-and-rebind
  gap. Code review caught the first implementation closing the probe before publishing — an
  unrelated process could take the port in that gap and the write-once allocation would then
  permanently name a port its publisher never owned. The storm's adversary test binds the
  allocated port immediately after publication and must get `EADDRINUSE`.
- **Durability of coordination state includes the LINK**: candidate fsync makes the bytes
  durable; a directory fsync after `link()` makes the publication durable. Writes go through a
  short-write-safe loop — `writeSync` may legally write short, and a short write published
  through the write-once path would be permanent. (The no-fsync decision three bullets up is
  scoped to snapshots — a derived cache — and deliberately does not reach coordination state:
  a lost allocation is not recomputable, it is a second singleton.)

## 4. Socket credential fallback

What T-011 implements, given §2's "no": runtime dir `/tmp/spendbar-<uid>` — **validated as the
primary isolation boundary** (lstat type, owner uid, non-symlink, mode **exactly** 0700; every
branch reachable via injected stats) — keyed on **uid** so the path length is bounded by
construction; a 32-byte token published **write-once via `link()`** with the publication made
durable by an fsync of the containing directory (exclusive-create-then-write would expose an
empty token to a concurrent first-run, which would then misclassify a live holder as foreign;
the race window itself is exercised via a `beforeLink` hook, not two sequential calls); token
comparison hashes both values and `timingSafeEqual`s the fixed-size **digests**, so wrong-length
and wrong-byte rejections share one code path — `timingSafeEqual`'s own length-mismatch throw is
a length oracle, and an early length return is a timing branch; both are gone by construction.
Token and allocation modes are validated **exactly** (0600), not "no group/world bits": a mode
this protocol never writes means something else wrote the file, which is what fail-closed exists
to surface.

Path rules, both downstream of §1's truncation finding:

- **Reject before `listen`** on `Buffer.byteLength(canonicalPath) > 104`. The canonical form:
  `/tmp` → `/private/tmp` adds 8 bytes, so the real runtime path is 34 bytes as the kernel sees
  it, not 26 as written. A test injects a realpath that pushes a fitting path over the limit and
  asserts `listen` is never reached.
- **Trusted root canonicalized first, then no symlinks strictly below it.** The implementation's
  own test caught the first version realpath'ing the whole parent — which resolves the very
  symlinks the rule refuses, so the guard could never fire. Root symlinkness (`/tmp` itself) is
  legitimate; a symlink inside the runtime dir is refused via `lstat` per component.
- **Traversal refused outright** — code review found (and I reproduced) that a textual
  root-prefix check passes `/tmp/../etc/svc.sock` and returns a canonical path OUTSIDE the root.
  Dot, dot-dot, and empty components are rejected before any path is built; there is no
  legitimate use for them in a runtime socket path, so the rule is refusal, not normalization.

Ownership validation takes **injected stat results**, making the foreign-uid branch (and every
other rejection) testable without root — this is the required gate; a privileged foreign-owned
fixture is separate integration evidence, since an always-unrunnable mandatory test makes a gate
infeasible, which is a different failure from a vacuous skip.

The probe rests on two legs, because a name scan alone is an inventory, not a detector (code
review's point, accepted): (1) the full prototype chain including Symbol keys NOMINATES
credential-suggestive names; (2) every nominee is verified SEMANTICALLY — it must actually yield
a numeric uid when invoked or read. An inert `SO_PEERCRED` constant is nominated and rejected
(false-positive fixture); an injected capability that returns `{uid}` flips the answer to yes
under a string key, a prototype key, and a Symbol key (falsifiability fixtures). The residual
blind spot — a real capability under a name the inventory misses — is closed by the recorded
review of Node 22's documented `net.Socket` surface, which the probe prints; no scanner can close
it without calling every function on the object. The conclusion is scoped to Node 22's supported
public API accordingly.

### 4.1 Corrections the implementation forced

Every one of these was a real defect found by code review and reproduced before being fixed;
they are recorded because a gate that reports only its successes is not evidence.

- **Path traversal (critical).** `/tmp/../etc/svc.sock` passed a textual root-prefix check and
  canonicalized to `/private/tmp/../etc/svc.sock` — outside the trusted root. Dot, dot-dot and
  empty components are now refused before any path is constructed.
- **Split-owner window at publication.** The first implementation closed its provisional listener
  *before* publishing, so an unrelated process could take the port in the gap and the write-once
  allocation would permanently name a port its publisher never owned. The publication winner now
  **retains** its listener and adopts it as the lock; the storm binds the allocated port in
  exactly that window and requires `EADDRINUSE`.
- **Single-use locks.** Re-acquiring a released `PortLock` "succeeded" while `held` stayed false
  and `release()` returned false — a listener bound and then leaked until process exit. Acquire
  and adopt now refuse on a spent or lost lock.
- **Domain separation was opt-out.** `purpose` and `allocationId` were optional and stringified,
  so two callers that both omitted them produced the identical transcript and authenticated as
  each other. Both are now required non-empty strings, validated at registration.
- **Request framing.** The holder replied as soon as 32 bytes had arrived, so "over-long requests
  are rejected" held only for the TCP segmentations the test happened to produce. The reply is
  now emitted at the request boundary (the challenger's half-close).
- **Manifest membership used `in`.** A live source named `toString` read as present in an empty
  candidate, and a new source named `constructor` did not count as an advance — `Object.hasOwn`
  now decides. Manifest offsets are also validated on the FIRST publish and on read, not only
  when a live snapshot exists to compare against.
- **Regressions were fixed but not PINNED.** The four bugs above were reproduced in a scratch
  script, fixed, and the permanent suite never asserted the exact failures — so a mutant restoring
  any of them would have left it green, which is the repo's own standard of evidence unmet. Each
  now has a named REGRESSION test, and all five corresponding mutations are caught.
- **Criterion 6 is checked over the whole production TREE, not the root manifest.** The first
  version was a pure function over `package.json` alone, which meant adding a dependency that
  declares its own `postinstall`, or that compiles on install, left the gate green — a consumer
  installs the transitive closure, not our manifest. `spikes/lifecycle.test.mjs` now enumerates the
  installed production tree with `npm ls --omit=dev --all --json --long`, collects each node's real
  installed PATH, and rejects `preinstall`/`install`/`postinstall` plus native builds (a
  `binding.gyp` file or a `gypfile` manifest flag) at every node. Collecting NAMES instead of paths
  was itself a defect found in round 15: it collapsed multiple versions of a package and skipped
  anything nested under a parent's own `node_modules`, so a clean hoisted copy masked a dirty nested
  one. The traversal is therefore a separate exported function with its own fixture proving a nested
  same-name package is visited, alongside one fixture per way a dependency can violate the rule.
  Measured on the current tree: 7 production packages (ccusage plus its six per-platform prebuilt
  binaries), no install hooks and no native build anywhere — the prebuilt binaries are downloaded
  artifacts, not compilation.

- **Portability.** The spikes were wired into `test:all` unconditionally, which breaks the
  repository-wide gate on Windows: they need `ps`, `process.getuid`, Unix-domain sockets, Unix
  permission semantics and `SIGKILL`. Gating the two Darwin-empirical *assertions* did not fix
  that, because the surrounding suites are POSIX-only regardless of what they assert. They are
  now split by requirement (`spikes/platform.mjs`): pure tests run everywhere, POSIX tests skip
  with a reason off POSIX, and the Darwin job must report **zero skips** so a skip cannot quietly
  become permanent where the gate was measured. Re-measured 2026-08-01 from the run that produces
  this claim, every column from ONE run: macOS (real) **106 passed / 0 skipped / 0 failed**;
  simulated linux **104 passed / 2 skipped / 0 failed**; simulated win32 **60 skipped / 26 passed /
  20 FAILED**. (These figures were
  stale for two rounds — they described a 51-test suite after it had grown — which is why they are
  re-measured from the same run rather than quoted from memory.)

  Those 20 win32 "failures" are artifacts of the simulation, not defects, and they are reported
  rather than filtered out because of what they demonstrate. Every one dies in `mkdtempSync` with
  `ENOENT ... mkdtemp 'undefined\temp/spendbar-publish-XXXXXX'`: `os.tmpdir()` ALSO branches on
  `process.platform`, so under the lie it reads `%TEMP%`/`%TMP%`, finds nothing on a macOS host, and
  returns a path built from `undefined`. The simulation cannot even reach the code it claims to
  exercise. That is the sharpest available statement of the point below — a platform column
  produced this way measures the harness, not the platform.

  **What that simulation does and does not establish, stated precisely, because I got this wrong.**
  Overriding `process.platform` changes which tests *run*. It changes nothing about the host: not
  the kernel's ephemeral port range, not `sun_path`'s limit, not filesystem semantics, not signal
  behaviour. I previously reported the linux column as portability verification, and review round 10
  found a genuine Linux-breaking bug sitting underneath it — a port-range check that would refuse
  valid kernel assignments on any host configuring `ip_local_port_range` below 49152 (Linux's
  default is 32768-60999). The simulation was structurally incapable of catching it, and reporting
  it as "linux verified" made a live defect look tested.

  So the accurate claim is narrow: **the platform split routes tests correctly, and nothing more.**
  Real Linux behaviour is unverified — no Linux host has run this suite. Open question 2 (must these
  prototypes pass on Linux, or is v0.2 macOS-only?) is therefore still genuinely open, and it now
  has a concrete cost attached: if Linux is in scope, this gate's evidence must be re-taken on a
  Linux host, not simulated. The port-range bug is fixed and pinned by a test acquiring port 40000,
  but that test proves the *rule* is right, not that the platform works.
- **The same bug three times, and what finally ended it (critical).** The write-once allocation has
  one governing rule: *once `link()` succeeds, nothing may throw*, because after that point the
  allocation is public and any escape closes the retained listener, leaving the file naming an
  unbound port. Round 6 found the post-link `fsync` could throw. Round 7 found the candidate cleanup
  could throw from a bare `finally` outside the capture. Round 8 found that
  `hooks.removeCandidate ?? ...` was still being *evaluated* after the link — and property access is
  not a safe operation, since a getter or a Proxy `get` trap runs arbitrary code. Three rounds, three
  correct fixes, none of which stopped it recurring, because each fixed the statement rather than the
  rule. The fix that held was structural: every hook is now read into a local *before* the link, so
  post-link there is nothing left to evaluate that could throw. The general lesson, which cost three
  rounds to learn: when the same defect returns in a new costume, the fix is at the wrong altitude.
- **A sweep that can be lied to is not a check (bootstrap harness).** The premature-entry sweep
  looks for children claiming the lock before the barrier opens. It exempted the child's own final
  result message — first by comparing the `result` *field*, then, after round 8, by object identity.
  Both were wrong, and the second is the instructive one: the early lie *arrives first*, so it
  becomes the child's recorded result, and an identity check then exempts precisely the message it
  was added to catch. No rule over message content can work, because the content is authored by the
  process under suspicion — every such rule is a specification for how to lie convincingly. The
  sweep now classifies each `entered` at receipt against a barrier flag only the parent writes,
  which is the one fact the child has no access to. Demonstrated by strengthening the mutant child

- **Durability of the publication, not just the bytes.** Candidate `fsync` was already there; the

- **The suite could not fail without hanging — and the "clean" runtime was itself a leak.** Two

  Two mutants were recorded here as **surviving deliberately**, with reasons. Review round 8
  refuted both, and the refutations are more useful than the original claims were.

  I wrote that removing the `await` from `release()`'s close callback "changes nothing observable",
  because libuv frees the port during the `close()` call itself. That conflates two different
  things: when the *port* frees is indeed unchanged, but the *settlement of the promise* is itself
  part of the contract and is directly observable — callers sequence work after `await release()`,
  and if it resolves early they are sequenced against nothing. Pinning it needed only a `close`
  whose callback the test controls, which separates settlement from the kernel-side release that
  made the two look identical.

  I also wrote that a loser skipping its probe close is detectable "only as a hang", because the
  leaked listener is internal to the module and invisible to the harness's resource registry. But
  the registry is not the only observer: the child process *passes that socket in*, so it can
  simply look at `probe.listening` after the call returns. The unreachability was in my test's
  design, not in the code.

  The common thread is worth more than either fix. Both claims were of the form "no test could
  detect this", and in both cases the honest statement was "no test I wrote detects this" — a
  claim about my imagination presented as a property of the system. Marking a mutant unpinnable
  ends the search, so the bar for it must be higher than for any assertion, not lower. **No mutant
  in this spike is now recorded as deliberately surviving.**

  One **equivalent mutant** is recorded, which is a different claim and a much weaker one. In
  `openBarrier`, swapping "set the flag" and "send the message" passes every run, and it should:
  Node dispatches IPC from the event loop, so no child reply can be processed between two
  synchronous statements in the parent. My first comment there justified the ordering by claiming
  the child "can reply faster than the next statement runs", which is simply false. The order is
  kept as defensive style against a future edit that puts something awaitable between the two lines,
  and it is credited with nothing further. The distinction matters: *equivalent* means the mutation
  changes no behaviour and no test could detect it; *surviving* means behaviour changed and my tests
  missed it. Only the first is a legitimate place to stop looking.

  The sweep that produced this also found a genuinely unpinned guard — the `barrierOpen` condition
  on the result assignment, which stops a child installing a fabricated result before there is
  anything to have a result about. Nothing exercised it, because the temporal sweep no longer reads
  `l.result` at all. It is now pinned by asserting the lying child's result was *refused*, not
  merely noticed: `mutant.result === null`.

- **"Read once" that read twice, in both branches (round 13).** The probe's `looksLikeCredential(v)`
  read `v.uid` to validate it and returned a boolean, after which each branch read the same getter
  AGAIN to build its message. Round 12 wrapped that in a try/catch, added a local, and I described
  the result as reading once. It did not. A `uid` getter returning 501 and then throwing turned a
  verified capability into an error; one returning 501 and then 0 recorded a UID that was never
  verified. The fix is structural rather than a rule to remember: `readCredentialUid(value)` performs
  the single read and returns what it read, so the verdict and the message are built from the same
  captured value and no caller *can* re-read.

  The reason the false claim survived two rounds is the more useful finding. A test existed and
  passed — a hostile getter that throws on FIRST access. Code that reads twice never reaches the
  second read, so it behaves identically and passes; and the test's `reads` counter was counting
  `peerCred` access, not `uid` access, so it measured the wrong quantity in the same way the
  round-8 challenge-deadline mutants did. The replacement fixture uses a **stateful** getter (valid
  uid first, garbage after) and asserts `reads === 1` on the getter itself. Applied to the code as
  it shipped, it fails on both branches.

- **A wedged release that could be reported but not survived (round 13).** `bootstrap.test.mjs`
  bounded `release()` with a timer and, on timeout, threw "lock release wedged" — into a runner that
  could not exit to print it, because racing a timer does not cancel the close and the accepted
  connections stay referenced. The child-exit branch three lines below had force-detached its
  handles since round 6. Same hook, same failure mode, one of two branches fixed: the ticket's most
  persistent defect, now on its fifth instance. `release()` also nulled `#server` on its first line,
  so the wedged listener was unreachable from outside — fixed by handing it to `#closing` for the
  duration of the close, with `__forceDispose()` as the teardown-only escape hatch.

- **An unfalsifiable line, removed rather than kept (round 13).** `disposeServer` originally called
  `server.unref()` as defence in depth. A mutant deleting it survived, so instead of arguing it was
  "obviously" protective I tried to build a test where it was load-bearing — and measured that the
  premise is false: once `close()` has been *requested*, the listening handle is already detached
  and the server alone no longer holds the event loop open. What holds it is the connections, which
  is why destroying them is the entire job. The line is gone and the reasoning is recorded, because
  a line that cannot fail reads as protection while providing none. This is the counterpart to the
  equivalent-mutant note above: there, the mutation genuinely changed nothing; here, the *code*
  genuinely did nothing.

- **The rename failure nothing reached (round 13).** `publishSnapshot`'s `committed` flag had two
  covered paths — fail-before-write and succeed-after-rename — and the third, `renameSync` itself
  throwing, was never exercised, so cleanup on that path was unverified. Real renames do fail
  (EXDEV across a bind mount, EACCES on the directory, ENOENT if the candidate was swept). It is now
  provoked without adding a rename hook to production: `beforeCommit` runs immediately before the
  rename, so removing the candidate there produces a genuine ENOENT. A mutant setting `committed`
  before the rename instead of after is caught.

- **The sibling audit, finally done deliberately (round 14).** After fixing the wedged-release gap
  in `bootstrap.test.mjs` I audited every other teardown for the same shape instead of waiting to be
  told. `portlock.test.mjs:139-140` had it — bounding `l.release()` and `s.close()` with a timer and
  disposing of neither — in the very file where the child-detach rule was written and sits fifteen
  lines below. That is the **sixth** instance of this ticket's dominant defect and the **first**
  found by audit rather than by a reviewer, which is the only reason it is worth recording
  separately: the pattern was diagnosed in round 8 and kept recurring for five more rounds because
  diagnosing it changed nothing about the procedure. The procedure is the fix — after any
  class-level correction, grep for the class and check every site before reporting.

  The audit's negative results matter as much as its hit, so they are stated: `lock.race.test.mjs`,
  `publish.test.mjs` and `auth.test.mjs` have directory-only teardowns with no bounded asynchronous
  operation and therefore nothing to dispose of, and `lifecycle.test.mjs` holds no resources at all.
  Five suites checked, one defect, three not-applicable, one empty — as opposed to "fixed the ones I
  happened to look at", which is what produced the previous five instances.

- **World-readable snapshots (critical, round 14).** `publishSnapshot`'s default candidate writer was
  `writeFileSync(f, text)` — no mode — so under the ordinary umask 022 the committed snapshot was
  **0644 and readable by every local user on the machine**. The snapshot holds the account's usage
  data. This is the third site of the umask class: the token learned it in round 12, the port
  allocation in round 13, and each fix carried a comment claiming the class had been swept. The
  round-13 comment even said "every file-creating call in the spike was checked, and this was the
  only other one whose mode is later asserted" — and that qualifier is precisely the hole. I audited
  for files that would FAIL a later mode check rather than for files created WITHOUT a mode, so the
  one file with no mode assertion at all was invisible to the audit that was supposed to find it. A
  narrow audit reads exactly like a complete one in the record it leaves behind.

  Now opened, `fchmod`'d and verified on the fd like the other two, plus an independent check on the
  candidate before the rename so an injected writer cannot publish a mode the rule would refuse.
  Pinned by a child-process test across umasks 022, 0200 and 077 — 022 fails open (the leak), 0200
  fails closed (the permanently-unreadable brick the token hit), and only exact-mode catches both.

- **What the sibling audit actually taught (round 14).** Round 14 found the disposal gap and the
  hook double-read in their siblings by audit, and I recorded that as the procedure working. The
  reviewer then found the snapshot permission bug, the allocation's missing pre-link cleanup guard
  (fourth site of *that* rule), and `identifyHolder` accepting an unvalidated deadline while its
  sibling `serveIdentity` validated one (second site). Three more sibling misses, in the same round
  that claimed the procedure was fixed. The honest conclusion is narrower than the one I wrote: the
  audit works for the class you think to name, and the recurring failure is not forgetting to audit
  but choosing the search term from the bug I was just shown. Every one of these was found by
  grepping for a *rule* ("every file this spike creates", "every deadline this spike accepts") and
  not for the symptom.

- **Two bugs from one conflated errno (round 14).** `publishToken`'s cleanup ran unconditionally, so
  an `openSync(candidate,"wx")` that failed EEXIST — a tag collision with another publisher already
  mid-flight — deleted a candidate this call never created, destroying that publisher's in-progress
  work. The same EEXIST was also read as "we lost the token link" although `linkSync` had never been
  reached, so the error was swallowed and the function went on to read a token that need not exist.
  EEXIST now carries that meaning only when it comes from the link, and cleanup is gated on having
  actually created the candidate. Invisible until round 14 because every existing test used a fresh
  tag, so the collision path was unreachable and the suite's teardown removed the residue silently.

- **Half-fixes, counted honestly (round 15).** Round 14 fixed three things and each fix was partial
  in the same way — it covered the statements I had been shown a failure in and stopped:
  - the pre-link cleanup guard covered creating and writing the allocation candidate and stopped at
    the link, so every non-EEXIST link failure (EACCES, ENOENT, EMFILE, EXDEV) still stranded it —
    and the regression test written for the guard threw *before* the link, so it stayed green over
    the surviving half;
  - the snapshot mode was verified *before* `beforeCommit`, so a hook could chmod the candidate to
    0644, or replace it with a symlink to a legitimate 0600 file, and the rename committed the
    object the check had already approved. `stat` also follows symlinks, so the check was reading
    the referent's mode while the symlink was what got published. Verification now runs after the
    hook, immediately before the rename, through `lstat`;
  - `SNAPSHOT_MODE` was documented as the rule for "every snapshot and candidate" while only the
    default writer enforced it, so a 0644 snapshot from an older build — or one planted by another
    local user — was read and trusted. The embedded checksum is no defence: it is unkeyed, so
    whoever can write the file can write a consistent one. The contract is now one function applied
    on both sides of the rename.

- **`adopt()`, the door nobody checked (round 15).** `publishAllocation` was taught in round 13 to
  refuse servers it cannot track, because a connection accepted before tracking starts is
  permanently unreachable and pins `release()` forever. `PortLock.adopt()` — the other entry point
  that takes a caller's listener — went on accepting raw servers for two more rounds, and one test
  adopted a raw server, which quietly normalized the unsafe path. Both doors now require
  `createWatchedServer()`.

- **The deadline class, third site (round 15).** `serveIdentity` validated its timeout; round 14
  added the same validation to `identifyHolder`; `probeOnConnectedUnixSocket` still passed
  `timeoutMs` straight to `setTimeout`, where 0/negative/NaN/Infinity report "the probe timed out"
  for an operation never given a chance — in the function whose entire output is this gate's answer.

- **What the sweeps found on their own (round 15).** Two defects were found by sweeping for a RULE
  rather than for the last symptom, and both were the same class as bugs the reviewer had already
  found elsewhere: the snapshot DIRECTORY was created with no mode at all (0755 under the ordinary
  umask, so other local users could list it and learn which sources exist and when they changed),
  and the two credential validators read every injected stat property twice — validate, then re-read
  to build the message — in the functions whose entire documented design is that the stat is
  caller-supplied. Fixing the directory took three attempts, each wrong in a way worth recording:
  `{recursive:true}` takes the umask; `{recursive:true, mode:0o700}` is umask-FILTERED, so under
  umask 0200 the first level is created 0500 and creating anything inside it fails EACCES; and
  recursive-then-chmod adjusts only the topmost directory mkdir created, leaving the one that
  actually holds the snapshot at the umask mode. Only creating one level at a time and chmod'ing
  each immediately is correct under every umask.

  The counterpart is also recorded: `readAllocation` has the same textual shape and was deliberately
  NOT changed, because its inputs are a real `fs.Stats` and a `JSON.parse` result — plain data, no
  accessor can run between two reads. Spreading the appearance of the rule to places it does not
  apply makes the real instances harder to find.

## 5. Lifecycle scripts (criterion 6)

"`npm ci --ignore-scripts` succeeded" proves nothing — it succeeds *by suppressing* scripts. The
executable check (`spikes/lifecycle.test.mjs`) is a pure function over the manifest asserting no
consumer install-time hook (`preinstall`, `install`, `postinstall`) and no attribution field, run
against the real `package.json` and mutation-tested by inserting each forbidden key into a fixture
and requiring the check to catch it. `prepare`/`prepack` are deliberately permitted: the packaging
contract *requires* them (they build `dist/` at pack time and on git-URL installs) and they do not
run on a registry install of a dependency — forbidding them would make the suite unsatisfiable.
