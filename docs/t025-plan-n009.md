## §2 SnapshotPayloadV1, field by field (F7)

Encoding: exact-key, canonically ordered — row tables sorted by row identity, every map sorted by
key. **Canonical tie behavior:** identities are unique by construction (below), so a duplicate
identity is never ordered — it is **rejected** by the constructor, per the duplicate rule.
**Duplicate rule, uniform across all six surfaces:** a duplicate row identity or duplicate model key
is a typed constructor rejection, never a silent merge and never last-wins. Merging would invent a
fact the producer did not state.

**Numeric discipline, uniform:** every cost is a finite non-negative `number`; every token count is a
non-negative **safe** integer (`Number.isSafeInteger`) — the bound `cnum` cannot express, and the one
`json.ts` already guards for the same reason (ALLOWLIST 7). Every field below is required and
non-null unless written `|null`.

```
SnapshotPayloadV1 {
  payloadVersion: 1
  surfaces: { <registry keys, exact set equality> : Row[] }
  totals:   { <the same keys>                     : ProducerTotals }
}
```

**`claude-instances`** — identity `(project, date)`.
`{ project: string, date: string, totalCost: cost, totalTokens: count, inputTokens: count,
outputTokens: count, cacheCreationTokens: count, cacheReadTokens: count, modelBreakdowns:
ModelBreakdown[] }`
`ModelBreakdown = { modelName: string, cost: cost, inputTokens: count, outputTokens: count,
cacheCreationTokens: count, cacheReadTokens: count }`, sorted by `modelName`, duplicate `modelName`
rejected.
**DECISION — `project` is the RAW producer key, never the cleaned name** (F7). `--instances` keys its
map by encoded project name; cleaning is display-time and configuration-dependent, so storing the
cleaned form would make an old snapshot change meaning when configuration changes — the same hazard
finding 6 raises for codex. Readers clean at render time.
Field is **`date`**, not `period` — pinned in both directions at `json.ts:327` / `json.ts:360`; the
normalizer must not unify them. `projects` legitimately absent on a genuinely empty result
(`json.ts:309-313`) → empty table.

**`all-daily`** — identity `(period)`. Same row fields, keyed `period`. Covers **all** agents
including GPT (`ccusage.ts:87`).

**`claude-blocks`** — identity `(startTime)`, **gap rows EXCLUDED** (F4).
`{ startTime: string, endTime: string|null, actualEndTime: string|null, isActive: boolean,
costUSD: cost, totalTokens: count, entries: count, tokenCounts: TokenCounts|null, models: string[] }`
`TokenCounts = { inputTokens: count, outputTokens: count, cacheCreationInputTokens: count,
cacheReadInputTokens: count }`; `models` is a string array, sorted, duplicates rejected.
**DECISION — exclude gap rows, verified against the fixture.** Round 1 said accepted gap rows may
carry only `isGap`; I verified it: **`tests/fake_ccusage.py:72` emits exactly `{"isGap": True}`, and
it sits in `blocks_normal()` — the NORMAL-case fixture, not an edge case.** A gap row therefore has
no honest identity, and deriving one from array position or neighbours would be inventing the
premise. The renderer skips gap rows already, so excluding them loses no view. Measured cost on real
data: 8 of 148 rows, all of which happen to carry `startTime` — real data does not exercise the
fixture's shape, which is exactly why the fixture governs. `isGap` is therefore not a stored field:
absence from the table IS the exclusion.

**`codex-sessions`** — identity **`rolloutStem`** (F5).
`{ rolloutStem: string, startInstant: string|null, sessionId: string|null, cwd: string|null,
cwdSource: "session_meta"|"unreadable"|"no-meta"|"bounds-exceeded",
projectId: string|null, projectNameAtIngestion: string|null,
cost: cost, tokens: count, models: {name: count} }`
**DECISION — identity is the rollout stem from `sessionFile`, NOT `sessionId` (F5).** Round 1 is
right and my round-1 reasoning was the defect class I claimed to be hunting. `codex.ts` **requires**
`sessionFile` and throws a frozen message without it; **no validator requires `sessionId`**. My
"5 506/5 506 distinct sessionId" proves uniqueness on one corpus — it proves nothing about
availability or stability across custom `CCUSAGE_CMD` output. `sessionFile` is the field the accepted
surface guarantees, and the rollout stem is what v2 §2 calls the rollout id. `sessionId` is kept as
optional data only.
**Attribution is stored, not re-derived (F6).** `projectId` and `projectNameAtIngestion` are resolved
**at the writer** from the rollout head's `session_meta`, plus surface-level `configIdentity` (§2.1)
recording the configuration that produced the mapping. Readers **aggregate the stored attribution and
never re-run cleanName over `cwd`** — doing so would make an old snapshot change meaning under new
configuration, which is precisely what N-009 finding 6 exists to prevent. Round 1 correctly noted my
prose promised this and my row shape omitted it.
**`CodexSessionRow.dir` is NOT a cwd** — it is a date directory (`'2026/07/09'`, `json.ts:462`).

**`codex-daily`** — identity `(date)`. `{ date: string, costUSD: cost, totalTokens: count }`.
`codexDaily` returns rows (`codex.ts:238`) but its **sole caller destructures only
`{ grand, grandTok }` (`codex.ts:494`)** — verified by grepping every reference — so no view reads a
row. Coverage still needs identities, so identity + the two counters are stored and nothing else.

**`claude-transcript-hours`** — **CONTINGENT, see ISS-090 and §7.** Intended identity
`(date, bucket, tz)`: `transcripts.ts:24` types buckets as `Map<label, Map<family, tokens>>` and
`scanTranscripts` runs **per date** (`transcripts.ts:114`), so `"09:30"` is a time-of-day, not an
instant, and the label alone collides across every day.

**`ProducerTotals`, per surface** (F7) — the producer's OWN totals, stored so readers can reproduce
the CLI's reconciliation cross-checks (finding 7). The shapes are not uniform and must not be
flattened into one:
- `claude-instances`, `all-daily`: `{ totalCost: cost, totalTokens: count }` — Claude spelling.
- `claude-blocks`: `{ costUSD: cost, totalTokens: count }`, computed over the **non-gap** rows the
  table stores, so totals and rows agree by construction.
- `codex-sessions`, `codex-daily`: `{ costUSD: cost, totalTokens: count }` — codex spelling
  (`totals.costUSD` / `totals.totalTokens`, deliberately unlike generic daily's `totalCost`).
- `claude-transcript-hours`: `{ totalTokens: count }` — no cost exists on this surface.

**§2.1 Surface-level metadata:** `configIdentity` (the cleanName configuration used at ingestion) is
stored once per payload, not per row, with a defined binding: it applies to every `codex-sessions`
row in the same generation.

## §3 Registry, and the two-stage normalization boundary (F9)

```
IngestionSurface {
  key, invocation,
  compat(raw)   -> AcceptedRows   // stage 1: reproduces the CLI's EXISTING accepted semantics
  normalize(AcceptedRows) -> Row[] // stage 2: builds the internal branded value
  watermark(Row[]) -> epochMs, identity(Row) -> string,
  disappearance: MirrorsProducerWindow | NoDisappearance,
  emptySentinel: 0
}
```

**DECISION — two stages, because one stage would reverse a recorded decision (F9).** A single
`normalize(raw)` with strict required fields **is** a runtime `CCUSAGE_CMD` validator, which
ISS-023/ISS-026 forbid — the same conflict ISS-089 records against T-013, recurring here in a sibling
ticket. The split resolves it without reversing anything:
- **Stage 1 imposes no new requirement on the producer.** It reproduces what the CLI accepts today,
  including the permissive shapes: `blocks` rows that are `{"isGap": True}` alone, an `isGap` value
  of `{}` (falsy in Python, truthy in JS — `tests/fake_ccusage.py:103`), `actualEndTime: ""` falling
  through to `endTime`, `directory` absent or null, `models` absent. Where the CLI tolerates, stage 1
  tolerates.
- **Stage 2 validates our own construction.** It may reject its own output as a programmer error,
  because both sides of that boundary are ours.
Differential fixtures cover every permissive shape `tests/fake_ccusage.py` already encodes, blocks
especially, asserting stage 1 agrees with the shipped CLI.

Invocations verified: `ccusage.ts:73` (instances), `:87` (all-daily), `:97` (blocks), `:104` (codex
sessions), `:118` (codex daily); the sixth is the writer-owned scan.

`sourceVersion` and `payload.surfaces` validate against the registry by exact set equality; a
contract test requires `SCHEMA_VERSION` (`envelope.ts:40`, currently 1) to change with the registry.
`retireSources` is not added.

## §5 Coverage — the horizon constants are GONE (F1)

**Round 1 was right and the repair is structural, not a tuning.** A declared horizon permits real
rows to vanish the day after it, on no evidence the producer prunes then; and my per-publish volume
cap was **resettable**, so repeated 10%-or-2-row losses erode the whole dataset while every single
transition passes. Counting vanished rows proves the size of a loss, never its legitimacy.

**So I measured what I had assumed.** Round 1's premise was that I could not distinguish producer
eviction from loss. Two measurements:

1. **`--since` IS honored on blocks**: `--since 20260801` returns 19 rows starting 2026-08-01. So the
   flag works.
2. **Yet `--since 20251211` returns the SAME 148 rows starting 2026-07-01** as no `--since` at all —
   while `all-daily` over the same corpus returns 190 rows back to 2025-12-11.

So `claude-blocks` genuinely holds ~35 days where the daily surfaces hold 237, and asking for more
does not produce more. Blocks recedes; the daily surfaces and codex-sessions do not. What I still
cannot witness is the RULE — whether it prunes at 30 days, 35, or on some other basis — which is
exactly why no constant belongs in this ticket.

**Two policies, both witnessable with no horizon constant:**

- **`MirrorsProducerWindow` — `claude-blocks` only.** N-009 §3 already decides the semantics: "the
  CLI's blocks view never showed more than ccusage's current window, so neither does the store", and
  no history is accumulated. For a surface whose contract IS to mirror the producer's current window,
  trailing recession is definitional rather than loss. Coverage still polices what a window slide
  cannot explain: **interior gaps and leading-edge loss (recent rows vanishing) refuse.** Both are
  detectable by pure comparison — no constant, no producer knowledge.
- **`NoDisappearance` — the five cumulative surfaces.** Daily rows for past days, past codex
  sessions, and past transcript buckets do not legitimately disappear; measured, all five span the
  full 237 days. **Any disappearance refuses**, typed, live generation retained. No horizon needed,
  because the answer is zero.

**Cumulative, not per-publish (F1).** The volume cap survives only as defence in depth on the mirror
surface, and it is a **cumulative budget against a recorded baseline**, not a resettable per-publish
percentage: the payload records, per surface, the oldest identity ever observed and the total
identities ever retired, and the budget is spent against that running total. A resettable cap is
precisely the erosion hole round 1 found.

**Activation of any finite horizon moves to T-012** (per L-006: the ideal moves to the ticket that
can witness it). T-012 runs the service and sees repeated publishes, so it can collect the
longitudinal transitions that would distinguish producer eviction from loss. Until it does, no
horizon exists anywhere in the codebase.

**DECISION — bootstrap is first-run ONLY (F2).** Round 1 is right that my round-1 rule was unsafe:
publishing as "bootstrap" over a manifest whose active generation is unusable bypasses the reset
protocol, lets an incomplete candidate replace the only recoverable baseline, and can leave the store
partial anyway because a valid manifest keeps retaining the corrupt generation. Tagging provenance
does not make it safe. Corrected:
- **No live manifest at all** → genuine first run → bootstrap publish, `refreshTier: "bootstrap"`.
- **Manifest exists but its active generation cannot supply a validated baseline** → typed
  **`baseline-unusable`** refusal. No publish. Recovery routes through the existing
  `startWriter`/`resetStore` path with all its hard stops, and only a genuinely emptied store then
  accepts a bootstrap.

**The witness chain, made atomic and detached (F3).** Round 1 correctly noted I named a witness
without a sequence, and that validating a payload does not make the ORIGINAL `payload` the branded
value — the "validated a copy, used the original" shape. Specified:

1. `publishSnapshot` reads the on-disk manifest and records its identity.
2. It reads **that exact** `activeGenerationId` through the internal read-by-id path.
3. Coverage consumes **only the detached branded value returned by the validator** — never
   `GenerationDoc.payload`, which remains `unknown` and is not read again after validation.
4. Manifest and container identities are re-checked **immediately before the first mutation**, with
   no intervening await (the standing `assertHeld` discipline). A changed manifest restarts or
   refuses; it never proceeds on the stale baseline.

**Outcomes**, coverage evaluated first, watermark never overriding it:

| Coverage | Watermark | Outcome |
|---|---|---|
| passes | dominates | `published` |
| passes | equal + any content update | `refreshed` |
| passes | equal + no change | `unchanged` — nothing written |
| **fails** | *(irrelevant)* | typed refusal; live generation retained |

## §7 What is contingent, and what proceeds anyway (ISS-090 / F8)

Round 1's finding 8 is correct and verification made it sharper. `scanTranscripts` applies a
**target-date-dependent per-file mtime filter** (`transcripts.ts:126`) **and** runs its
`[requestId, message.id]` dedupe at `:171` — **before** the record's own date is tested at `:178`.
So the surviving file set is date-dependent, which makes the `seen` set date-dependent, which makes
duplicate winners date-dependent. One global pass cannot reproduce 190 per-date passes, and the
difference is not a fixed offset. Storing enough to re-derive it would mean per-record state for the
whole corpus. 190 real passes would cost ~100 minutes.

That is an owner decision (ratify a behavioral change to `hourly --cached`, cut the surface, or
accept the cost) and it is filed as **ISS-090 (critical)**. It is not a planner's to make.

**T-025 proceeds regardless, and this is deliberate.** The five other surfaces are unaffected and
fully specified above; items 1, 2 and 5 are independent; §5's policies and §3's two-stage boundary
are surface-generic. Only `claude-transcript-hours`'s registry entry is held. If the owner cuts the
surface, the registry drops to five keys and `SCHEMA_VERSION` moves — a one-line registry edit,
because the registry is the single definition point. That is the design paying for itself.

## §11 Risks

The design's obligations repeat **six times**, which is this project's recurring "fixed at one site,
not its siblings" shape — hence the per-surface test enumeration in §8 rather than one parameterized
case. Coverage now decodes the live payload on every publish (2.80 MiB today, bounded at 32 MiB), so
publish is O(payload) — which is why `unchanged` writing nothing matters. `NoDisappearance` is
deliberately strict: if a cumulative producer ever *does* prune, publishes refuse until T-012
supplies an evidenced horizon — fail-closed and visible, which is the correct direction, but it will
be reported as a bug and should be recognized. `codex-sessions` stores resolved cwds, i.e. real user
paths, in the user's own store — correct for the runtime artifact, forbidden in fixtures, where the
packaging content scan already enforces placeholders.
